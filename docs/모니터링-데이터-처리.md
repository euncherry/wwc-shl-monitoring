# 히어링루프 모니터링 데이터 처리 (현재 구현 기준)

> 개발 제품(히어링루프)의 3대 핵심 운영 상태를 **하드웨어 → AWS IoT Core(MQTT 브로커) → 백엔드(NestJS) → 프론트엔드(React)** 경로로 수집·감시하는 방식을 실제 구현 기준으로 정리한다.
> 장애 판정은 **연결 끊김 지속** 기준, 임계값은 **4시간**으로 확정 운영한다.
> 근거: 백엔드(NestJS)·프론트(React) 코드 + SHL MQTT Protocol (2026-07-13 문서 v4.0 / proto v4.4).

---

## 1. 전체 데이터 경로

```
[히어링루프 기기]  --MQTT-->  [AWS IoT Core (브로커)]  -->  [백엔드]  --REST/SSE-->  [프론트엔드]
```

기기 상태는 두 종류의 신호로 수집된다.

| 구분 | 발생 주체 | 내용 | 백엔드 반영 |
|---|---|---|---|
| **(A) 연결 상태** | **AWS IoT Core(브로커) 자동 감지** | MQTT 연결/해제(세션·keepalive 기반) | `connection_status`, `disconnected_at` |
| **(B) 앱 메시지** | **기기가 직접 발신** | HelloRequest·StatusReport 등 | 아래 각 필드 |

### 기기 발신 MQTT 메시지(B)와 반영 필드

| 메시지 | 담긴 데이터 | 반영 필드 |
|---|---|---|
| **HelloRequest** (최초 연결 시) | WiFi(ESP32)·HL(Nordic) 펌웨어 버전 | `wifi_firmware_version`, `hl_firmware_version`, 설치 세트(`firmware`) |
| **StatusReport** (이벤트 기반 발신) | 과열 여부(`gpio_state`), Wi-Fi 신호(`wifi_rssi_dbm`), Wi-Fi SSID(`wifi_ssid`) | `last_seen_at`, `last_gpio_state`, `last_wifi_rssi_dbm`, 상태이력(`status_log`) |
| ErrorReport / UpdateReport / DeviceLog | 에러·OTA 진행·기기 로그 | 각 로그 |

> `connection_status` 값은 **OFFLINE / ONLINE / UPDATING** 세 가지이며 다음으로 갱신된다.
> - 브로커 연결 이벤트: `connected` → ONLINE, `disconnected` → OFFLINE(+`disconnected_at` 기록)
> - StatusReport 수신 시: (OTA 중이 아니면) ONLINE 확정
> - 펌웨어 전송 중: UPDATING

## 2. 3대 모니터링 상태 (현재 구현)

> 📌 이 섹션(①②③)의 **시험성적서 제출본**은 [시험성적서-표시규격.md](시험성적서-표시규격.md)에 별도로 동결 보관한다.
> 이 문서는 구현 변경에 따라 계속 갱신되지만, 제출본은 확정 이후 갱신하지 않는다(변경 시 개정 이력 추가).

### ① 전원 상태 (ON / OFF)

- **판정 근거**: 전원이 인가되어야만 기기가 AWS IoT Core(MQTT 브로커)에 연결되므로, 브로커가 실시간 자동 감지한 연결 상태(`connection_status`)를 전원 판정의 확정 지표로 사용한다 — **OFFLINE이 아니면 전원 ON, OFFLINE이면 전원 OFF**. 단 이 판정은 **설치·프로비저닝이 완료된 기기(`status = ACTIVE`)** 를 대상으로 하며, 아직 최초 연결 전인 `PENDING` 기기는 전원 꺼짐이 아니라 **'프로비저닝 대기'로 구분해 표시**한다.
- **수신 데이터**: 모니터링 웹은 백엔드 `DeviceResponseDto`의 `status`·`connection_status`를 받아 표시한다.

| `status` (DeviceStatus) | 의미 |
|---|---|
| `PENDING` | 화이트리스트 등록 완료, IoT 프로비저닝 대기 중 |
| `ACTIVE` | IoT Core 프로비저닝 완료, 정상 운영 중 |

| `connection_status` (ConnectionStatus) | 의미 |
|---|---|
| `OFFLINE` | 연결 끊김 |
| `ONLINE` | 정상 운영 중 |
| `UPDATING` | 펌웨어 업데이트 진행 중 |

> 전원 ON 판정에는 `ONLINE`과 `UPDATING`이 모두 포함된다(연결이 성립한 상태이므로).

- **표시 정책(모니터링 페이지)**: 전원 상태를 아이콘 + 색상으로 표시한다.

| 상태 | 아이콘 | 색상·라벨 |
|---|---|---|
| 켜짐 (`ONLINE`·`UPDATING`) | 전원(⏻) 아이콘 | 🟢 초록 **"ON"** |
| 꺼짐 (`OFFLINE`) | 전원 사선(⏻⃠) 아이콘 | ⚪ 회색 **"OFF"** |
| 프로비저닝 대기 (`status = PENDING`) | 시계(🕐) 아이콘 | ⚪ 회색 **'프로비저닝 대기'** 뱃지를 전원 표시와 함께 노출 |

**관리자 페이지 — 실시간 그대로** (운영·점검용)

연결이 끊기면 **즉시** ⚪ 회색 'OFF'로 표시한다. (목록 표에서는 공간상 아이콘만, 상세 모달·모바일 카드에서는 아이콘 + 'ON/OFF' 라벨을 함께 표시)

**사용자(기관) 페이지 — 미연결 지속 시간 기준** (②·③과 동일한 3단계 정책)

| 미연결 지속 | 전원 표시 |
|---|---|
| **24시간 미만** | 🟢 초록 **"ON"** (야간 소등 같은 일상적 전원 차단은 문제로 표시하지 않음) |
| **24시간 이상** | ⚪ 회색 **"OFF"** (🔴 연결 끊김 뱃지와 함께 진짜 상태 노출) |

### ② 기기 동작 여부 (정상 작동 / 작동 중지)

- **판정 근거**: 연결이 끊기면 백엔드가 끊긴 시각(`disconnected_at`)을 기록하고 재연결 시 초기화하며, 이 시각으로 **미연결 지속 시간**을 계산해 기기 동작 여부를 판단한다.
- **표시 정책(모니터링 페이지)**: 동작 상태를 아이콘 + 색상으로 표시하며, 역할에 따라 다르게 표시한다.

| 상태 | 아이콘 | 색상·라벨 |
|---|---|---|
| 정상 작동 | 활동 파형 아이콘 | 🟢 초록 **"정상 작동"** |
| 업데이트 중 | 회전 화살표 아이콘 | 🔵 파랑 **"업데이트 중"** (펌웨어 원격 업데이트 진행) |
| 작동 중지 | 가로선(—) 아이콘 | ⚪ 회색 **"작동 중지"** |

**역할별 기준 — 관리자 4시간 / 사용자 24시간**

관리자 페이지(운영·점검용)는 연결이 끊기면 **즉시** '작동 중지'로 표시한다(전원 OFF, WiFi는 실값 '끊김'). 백엔드 서버는 **30분 주기로 전체 기기를 자동 점검**하여(§3 참조), 미연결이 **4시간** 이상 지속된 ACTIVE 기기에 '연결 끊김' 장애 알림(긴급)을 알림센터에 자동 생성한다. 사용자(기관) 페이지는 야간 소등 같은 일상적 전원 차단이 장애로 보이지 않도록, 미연결이 **24시간** 이상 지속된 경우에만 '연결 끊김'으로 표시한다.

| 미연결 지속 | 관리자 페이지 | 사용자(기관) 페이지 |
|---|---|---|
| 4시간 미만 | 작동 중지 (즉시 반영) | 정상 작동 |
| **4시간** 이상 | 작동 중지 + 🔴 **장애 알림 생성** | 정상 작동 (WiFi만 회색 '끊김') |
| **24시간** 이상 | 작동 중지 | 🔴 **연결 끊김** |

**장애 알림 임계값 설정** — 장애 알림 기준(4시간, `connection_lost_hours`)은 **관리자 알림센터 → 알림 설정에서 조정 가능**(`GET·PATCH /alerts/settings/thresholds`, 관리자 전용, 최솟값 1). ⚠️ 사용자 페이지의 24시간(연결 끊김 표시)·4시간(WiFi 끊김 표시)은 **프론트 고정 상수**(`userDeviceDisplay.ts`)로, 이 설정과 무관하다.

### ③ 네트워크 연결 상태 (Wi-Fi)

- **판정 근거**: 기기가 보고하는 Wi-Fi 신호세기 원시값(`wifi_rssi_dbm`)을 백엔드가 4단계 등급(`wifi_signal`)으로 산출하고, 프론트는 이 두 필드로 네트워크 연결 상태를 표시한다 — **강함**(RSSI ≥ -55dBm) / **보통**(-67 ~ -55dBm) / **약함**(< -67dBm) / **끊김**(연결 해제 또는 RSSI 미수신).
- **표시 정책(모니터링 페이지)**: 신호 등급을 Wi-Fi 아이콘 + 색상으로 표시한다.

| 등급 | 기준 | 아이콘 | 색상·라벨 |
|---|---|---|---|
| 강함 | RSSI ≥ -55dBm | Wi-Fi 호 3개(가득) | 🟢 초록 **"강함"** |
| 보통 | -67 ~ -55dBm | Wi-Fi 호 2개 | 🟢 초록 **"보통"** |
| 약함 | < -67dBm | Wi-Fi 호 1개 | 🟠 주황 **"약함"** |
| 끊김 | 연결 해제·RSSI 미수신 | Wi-Fi 사선(⃠) | 🔴 빨강 **"끊김"** |

**관리자 페이지 — 실시간 그대로** (운영·점검용)

위 등급을 실값 그대로 표시한다. **아이콘에 등급별 색상**을 적용하고 라벨(강함/보통/약함/끊김)과 **RSSI 원시값(dBm)** 을 함께 표시한다(원시값은 신호 단계 검증용 임시). 연결이 끊기면 **즉시 '끊김'**(빨간 사선 아이콘).

**사용자(기관) 페이지 — 미연결 지속 시간 기준 3단계** (①·②와 동일 정책)

연결 중에는 위 등급을 색상 칩으로 표시한다(강함·보통=초록 칩, 약함=주황 칩). 미연결 시에는 빨간 '끊김' 대신 지속 시간에 따라:

| 미연결 지속 | WiFi 표시 |
|---|---|
| **4시간 미만** | 🟢 초록 칩 **"정상"** (Wi-Fi 아이콘) |
| **4~24시간** | ⚪ 회색 칩 **"끊김"** (사선 아이콘 — 은은하게, 문제를 WiFi 연결로만 드러냄) |
| **24시간 이상** | **"—"** (🔴 연결 끊김 뱃지와 함께 진짜 상태 노출) |

## 3. 장애(연결 끊김) 자동 판정

| 항목 | 내용 |
|---|---|
| 점검 주기 | 30분 (백엔드 스케줄러 Cron `EVERY_30_MINUTES`) |
| 대상 | 프로비저닝 완료(ACTIVE) 기기 |
| 조건 | `connection_status = OFFLINE` 이고 연결 끊김 시점(`disconnected_at`) 이후 **4시간 초과** |
| 결과 | **연결 끊김(CONNECTION_LOST)** 알림 생성, 우선순위 **CRITICAL** |
| 임계값 | `connection_lost_hours = 4시간` (알림 설정에서 조정 가능하나 현재 4시간으로 확정 운영) |

## 4. 프로비저닝 상태 & 펌웨어 업데이트(OTA) 조건

- **프로비저닝 상태**
  - `PENDING`: 화이트리스트에 등록만 된 상태(최초 연결 전). → 연결 없음(OFFLINE).
  - `ACTIVE`: 최초 연결(프로비저닝) 완료.
- **OTA 전송 조건**: 백엔드는 대상 기기가 **`connection_status = ONLINE`일 때만** 펌웨어 전송을 허용한다(그 외에는 거부). 즉 **전원 ON + 네트워크 연결 + 동작(ONLINE)** 이 모두 성립해야 업데이트가 가능하다.
  - `PENDING`/`OFFLINE` 기기는 OTA 불가.
  - 전송 중에는 `connection_status = UPDATING`으로 전환된다.

## 5. 브로커(AWS IoT Core)의 역할

기기와 백엔드는 서로 직접 통신하지 않고, 그 사이의 MQTT 브로커(AWS IoT Core)를 경유한다.

1. **연결 유지·인증** — 모든 히어링루프 기기가 상시 붙어있는 접속점. 기기별 인증서(TLS)로 인증하고 MQTT 세션을 유지(keepalive)합니다.
2. **메시지 중계 (pub/sub)** — 기기와 백엔드는 서로 직접 통신하지 않고 항상 브로커를 거칩니다. 기기가 토픽에 발행(publish)하면 브로커가 백엔드로, 백엔드가 명령을 발행하면 브로커가 기기로 전달하는 양방향 우체국.
3. **연결 상태 자동 감지 (presence/lifecycle)** — 기기가 붙었는지/끊겼는지를 브로커가 스스로 압니다(TCP·MQTT keepalive로). connect/disconnect 이벤트를 자동 발행 → 백엔드 `connection_status`. ← 전원 ON/OFF·네트워크 연결 판정의 근거가 바로 이것.
4. **라우팅** — 들어온 메시지를 규칙(Rule)에 따라 큐(SQS)/Lambda로 흘려보냄.

### 이 시스템의 실제 흐름 (코드 기준)

```
기기 --MQTT publish--> [IoT Core 브로커] --Rule--> SQS --> 백엔드(polling)
        (HelloRequest·StatusReport·에러·OTA진행·로그)

[IoT Core presence(연결/해제)] --> Lambda --> 백엔드 lifecycle-callback --> connection_status

백엔드 --publish--> [IoT Core 브로커] --> 기기
        (명령·OTA 알림·응답)
```

### 왜 모니터링에서 핵심인가

- 전원·네트워크 상태를 별도 감시 회로/신호 없이 "브로커 연결 여부"로 대체할 수 있는 이유가 3번(연결 자동 감지)입니다. 브로커가 각 기기의 붙음/끊김을 알아서 감시해주니, 백엔드는 그 이벤트만 받아 `connection_status`로 쓰면 됩니다.
- 한마디로 브로커는 **"메시지 우체국 + 기기 출석부"** 역할이에요. 출석부(연결 감지)가 **①전원·②동작·③네트워크(연결 여부)** 를, 우체국으로 오가는 앱 메시지(StatusReport)가 **과열·Wi-Fi 신호세기·마지막 정상신호 수신 시각**을 채웁니다.

## 7. 요약 (수집 → 처리 → 표시)

| 모니터링 상태 | 수집(무엇을) | 처리(백엔드) | 표시(관리자 — 실시간) | 표시(사용자 — 지속시간 기준) |
|---|---|---|---|---|
| ① 전원 ON/OFF | MQTT 연결 수립/해제(브로커 자동 감지) | `connection_status`·`disconnected_at` | 전원 ON / OFF (즉시) | 24h 미만 ON · 24h 이상 OFF |
| ② 기기 동작 여부 | 연결 상태 + StatusReport(이벤트 기반) | `connection_status`·`last_seen_at`·`status_log`, 연결 끊김 4h 지속 시 장애 알림 | 정상 작동 / 업데이트 중 / 작동 중지 (즉시) | 24h 미만 정상 작동 · 24h 이상 🔴 연결 끊김 |
| ③ 네트워크(Wi-Fi) | MQTT 연결 + Wi-Fi 신호세기(RSSI) | `connection_status`·`wifi_signal`·`wifi_rssi_dbm` | 강함/보통/약함/끊김 + RSSI(dBm) | 4h 미만 정상 · 4~24h 회색 '끊김' · 24h 이상 '—' |

> 연결 중일 때는 두 페이지 모두 동일한 실값(강함/보통/약함, 정상 작동 등)을 표시한다. 차이는 **연결이 끊긴 뒤**에만 발생한다.
